# rust_pii_transformer

> **한국어 특화 개인정보(PII, Personally Identifiable Information) 탐지·마스킹 코어 라이브러리**
>
> 한국어 텍스트에서 개인정보를 **결정적으로(deterministic)** 탐지하고,
> **원문 복원이 보장되는** 마스킹을 수행하는 **모델 없는 순수 Rust** 라이브러리.

이 문서는 이 라이브러리의 **완결형 개발자 매뉴얼**이다. 왜 만드는지, 무엇을 하고 무엇을 하지 않는지,
핵심 자료구조와 알고리즘 설계, 공개 API, 명령줄 도구(CLI)와 Python 바인딩, 빌드와 테스트, 개발 로드맵,
그리고 **현재 구현되지 않은 범위**까지 모두 담는다.

**현재 상태: 오프셋 매핑 층과 그 Python 바인딩만 구현돼 있다.**
[6. 오프셋 매핑 설계](#6-오프셋-매핑-설계)의 `span` 모듈은 동작하고 테스트를 통과하며,
[15. Python 바인딩](#15-python-바인딩)으로 그 층을 Python 에서 쓸 수 있다.
정규화 패스, 탐지, 마스킹은 아직 없다. 나머지 절의 코드는 확정된 설계안이며
실제 동작하는 코드가 아니다. 진행 상황은 [17. 개발 로드맵과 현재 상태](#17-개발-로드맵과-현재-상태)에 3단계
(동작 확인 / 코드만 존재 / 미구현)로 구분해 기록한다.

**배포 상태: 아직 어디에도 게시하지 않았다.** 패키지 이름이 약속하는 탐지·마스킹이 없는 동안은
crates.io 와 PyPI 어느 쪽에도 올리지 않는다. 검색으로 유입된 사람이 개인정보 탐지를 기대하고
설치하는 일을 만들지 않기 위해서다. 게시 기준은 [17.1 배포 전 관문](#171-배포-전-관문)에 적는다.

## 1. 왜 이 라이브러리가 필요한가

### 시장 공백

한국어 개인정보 탐지에는 실재하는 공백이 있다. 2026년 7월 기준 조사 결과다.

| 기존 도구 | 한국어 지원 | 한계 |
| --- | --- | --- |
| Microsoft Presidio | 한국 전용 인식기 5종 (주민등록번호, 외국인등록번호, 사업자등록번호, 운전면허번호, 여권번호) | 파이썬 전용. **순수 숫자열을 전제**하므로 변형 표기를 못 잡는다. **한국 계좌번호 인식기가 없다** (국제 계좌번호 규격은 한국에 적용되지 않는다) |
| GLiNER2-PII | 없음 | 영어, 프랑스어, 스페인어, 독일어, 이탈리아어, 포르투갈어, 네덜란드어 7개 언어만 지원 |
| Piiranha | 없음 | 영어 중심 |
| korean-pii (오픈소스 파이썬 구현) | 있음 | 파이썬 서비스 형태. 설계 참고 대상이지 라이브러리로 쓸 성숙도는 아니다 |

**순수 Rust 로 된 한국어 개인정보 탐지 라이브러리는 사실상 존재하지 않는다.** 이것이 이 프로젝트의 첫 번째 이유다.

### 우리가 이겨야 할 지점

규칙 기반 탐지의 속도 우위는 이미 증명돼 있다. Presidio 는 중앙값 15밀리초로 트랜스포머 계열 탐지 모델보다
8-11배 빠르다. 그러나 두 개의 구멍이 있다.

- **원문 복원 실패.** Presidio 는 토크나이즈 불일치 때문에 문서의 36퍼센트에서 원문 완전 복원에 실패한다.
  마스킹 결과에서 원문을 되돌릴 수 없으면 컴플라이언스 도구로 쓸 수 없다.
  **이 라이브러리는 [6. 오프셋 매핑 설계](#6-오프셋-매핑-설계)로 이 문제를 정면으로 푼다.**
- **변형 표기 미탐.** 순수 숫자열만 전제하면 한글 수사 표기(`팔팔공일공일`), 띄어쓰기와 구분자 변형
  (`880101 - 1234567`), 한글과 숫자 혼합 표기(`88년 1월 1일생`)를 통째로 놓친다.
  **변형 표기 인식이 이 라이브러리의 존재 이유다.**

### 규칙 기반의 정직한 한계

다국어 벤치마크 REDACT(25개 언어, 51개 엔티티)에서 규칙 기반 탐지기는 고민감도 항목 재현율 0.07 로 무너졌다.
규칙만으로 모든 개인정보가 잡히지는 않는다. 그래서 이 라이브러리는 **규칙으로 확실하게 잡히는 것에 집중하고,
잡히지 않는 범위를 숨기지 않고 문서화한다**([18. 알려진 한계](#18-알려진-한계)).

## 2. 핵심 특징

| 특징 | 의미 |
| --- | --- |
| **변형 표기 인식** | 순수 숫자열뿐 아니라 한글 수사 표기, 구분자와 띄어쓰기 변형, 한글과 숫자 혼합 표기를 정규화 층에서 흡수한다 |
| **원문 복원 보장** | 정규화와 동시에 역방향 구간 정렬 테이블을 만든다. 탐지 스팬은 항상 원문 바이트 구간으로 정확히 되돌아간다 |
| **판정 근거 출력** | 어떤 규칙이 매칭됐고, 어떤 체크섬을 통과했고, 어떤 문맥 단서가 잡혔고, 어떤 정규화가 적용됐는지를 함께 낸다. "왜 걸렸는가"와 "왜 안 걸렸는가"를 둘 다 설명할 수 있다 |
| **모델 없음** | 모델 파일 0개, GPU 0, 외부 API 호출 0, 네트워크 접근 0. 폐쇄망에서 그대로 돈다 |
| **결정적** | 같은 입력이면 항상 같은 출력. 캐싱, 테스트, 감사 추적이 성립한다 |
| **자기완결** | 기본 빌드는 순수 Rust, 외부 함수 인터페이스(FFI, Foreign Function Interface) 0, 하위 프로세스 호출 0. 다른 언어 런타임을 요구하지 않는다 |

## 3. 설계 원칙

**정규화는 관대하게, 검증은 엄격하게.**

이 라이브러리의 중심 판단이다. 정규화 층은 의심스러운 후보를 넉넉히 만들어 낸다. 한글 음절 `사구` 를
숫자 `49` 로 읽는 것 같은 과잉 변환도 허용한다. 대신 탐지 층이 체크섬, 날짜 유효성, 문맥 단서로 걸러낸다.
주민등록번호처럼 검증 수단이 강한 엔티티는 잘못된 정규화가 통과할 확률이 사실상 0 이다.
반대로 정규화를 보수적으로 하면 변형 표기를 놓치고, 그것이 이 라이브러리가 존재하는 이유를 없앤다.

이 원칙에는 대가가 따른다. 검증 수단이 약한 엔티티(계좌번호, 생년월일)는 관대한 정규화가 그대로 오탐이 된다.
그래서 **정규화 비용을 신뢰도에서 차감**한다([9. 탐지 층 설계](#9-탐지-층-설계)).

### 나머지 원칙

- **원자성.** 정규화로 만들어진 구간을 탐지 스팬이 반으로 가르지 못한다. 가르면 구간 경계 바깥으로 넓힌다.
- **단조성.** 모든 정규화 연산은 순서를 보존한다. 이 성질 덕분에 역방향 매핑이 이진 탐색으로 끝난다.
- **한 방향으로만 확장.** 규칙으로 못 잡는 항목(이름, 주소)은 별도 개체명 인식(NER, Named Entity Recognition)
  백엔드를 나중에 옵트인으로 붙일 수 있도록 인터페이스만 열어 둔다. 코어에는 넣지 않는다.

## 4. 범위와 비목표

### 하는 것 (v0.1)

- 정규화: 한글 수사 역변환, 공백과 구분자 정규화, 전각과 유사문자 정리, 역방향 오프셋 매핑
- 탐지: 정규화 문자열에서 패턴 매칭 후 체크섬과 문맥으로 검증. 판정 근거 동반 출력
- 마스킹: 정책 선택(전체 치환, 부분 노출, 해시, 토큰화)과 원문 복원 보장
- 합성 검증 데이터 생성: 체크섬이 유효한 샘플과 변형 표기 샘플

### 하지 않는 것

- **머신러닝 모델을 쓰지 않는다.** 모델 파일, GPU, 외부 API, 네트워크 접근 모두 0
- **이름과 주소는 v0.1 범위 밖이다.** 규칙이 없는 항목이다. 인터페이스만 열어 두고 구현하지 않는다
- **문서와 이미지 파싱을 하지 않는다.** 이 라이브러리의 입력은 텍스트다. 문서에서 텍스트를 뽑는 일과
  이미지에서 글자를 뽑는 일은 이 패밀리의 다른 엔진이 담당한다
- **특정 언어 런타임에 종속되지 않는다.** Rust 라이브러리가 정본이고, Python 바인딩은 그 위의 얇은 층이다

## 5. 아키텍처

3층 파이프라인이다. 각 층은 독립적으로 테스트 가능하다.

```text
원문 텍스트
   ↓
[1층] 정규화 파이프라인
   유니코드 정규화 형식 C(NFC) → 전각·유사문자 폴딩 → 한글 수사 역변환 → 구분자 정규화
   ↓  출력 2개: 정규화 문자열, SpanMap(역방향 구간 정렬 테이블)
   ↓
[2층] 탐지
   숫자 런 스캐너 → 엔티티 후보 분류 → 체크섬 검증 → 문맥 점수 → 신뢰도 산정
   ↓  출력: Finding 목록 (정규화 스팬 기준)
   ↓
   SpanMap.to_source() 로 원문 스팬 복원 (경계 스냅 포함)
   ↓
[3층] 마스킹
   정책 적용(전체 치환 / 부분 노출 / 해시 / 토큰화)
   ↓  출력: 마스킹 텍스트, Finding 목록, 복원 맵(토큰화 정책일 때)
```

핵심은 **1층과 2층 사이에 SpanMap 이 끼어 있다는 점**이다. 탐지는 깨끗한 정규화 문자열 위에서 하고,
마스킹은 원문 위에서 한다. 그 둘을 잇는 것이 SpanMap 하나뿐이므로, 복원 정확성의 책임이 한 곳에 모인다.

## 6. 오프셋 매핑 설계

**이 절이 이 라이브러리의 최대 차별점이다.** Presidio 가 문서의 36퍼센트에서 실패하는 지점이 정확히 여기다.

### 문제

정규화는 네 가지를 모두 한다. 문자를 지우고(하이픈 흡수), 바꾸고(전각 숫자를 반각으로),
늘리고(`일억` 이 숫자 9자리로), 줄인다(`구십일` 이 숫자 2자리로). 그래서 원문과 정규화문 사이에
1대1 대응이 성립하지 않는다. 그러나 **순서는 항상 보존된다.** 이 단조성이 해법의 기반이다.

### 자료구조: 단조 구간 정렬 테이블

문자별 인덱스 배열 대신 **세그먼트 테이블**을 쓴다. 항등 구간을 하나로 접으므로 실텍스트에서 항목 수가
수십 개 수준이고, 이진 탐색으로 조회하며, 무엇보다 **어떤 규칙이 이 구간을 만들었는지**를 함께 담을 수 있다.
판정 근거 출력이 여기서 공짜로 나온다.

```rust
/// 정규화 전후를 잇는 단조 구간 정렬 테이블.
/// dst(정규화문) 기준으로 정렬되어 있고, 양쪽 텍스트를 빠짐없이 덮는다.
pub struct SpanMap {
    segments: Vec<Segment>,
}

/// 정규화 한 조각. 연속한 Identity 구간은 하나로 접어 저장한다.
pub struct Segment {
    /// 입력(원문) 쪽 구간
    pub src: Span,
    /// 출력(정규화문) 쪽 구간
    pub dst: Span,
    pub kind: SegmentKind,
    /// 이 구간을 만든 정규화 규칙들. 판정 근거에 그대로 실린다.
    /// 적용 순서가 아니라 이름 오름차순으로 정규화된다(아래 "규칙 목록은 왜 정렬하는가").
    pub rules: Vec<RuleId>,
    /// 이 구간 하나의 정규화 비용
    pub cost: NormalizationCost,
}

pub enum SegmentKind {
    /// 원문 그대로
    Identity,
    /// 치환 (전각 숫자를 반각으로, 유사문자 교정)
    Replace,
    /// 원문에만 존재 (하이픈, 공백, 점 흡수)
    Delete,
    /// 정규화문이 더 길다 (한글 수사를 숫자로)
    Expand,
    /// 원문에 대응이 없다 (현재 파이프라인 미사용, 확장 대비)
    Insert,
}
```

### 바이트와 문자 오프셋을 둘 다 저장한다

Rust 문자열 슬라이싱은 바이트 인덱스를 쓰고, Python 과 JavaScript 소비자는 문자 인덱스를 쓴다.
한국어는 음절 1자가 UTF-8 로 3바이트라 둘이 항상 다르다. 나중에 변환하면 매번 O(n) 스캔이 붙으므로
세그먼트에 처음부터 함께 넣는다.

### 파이프라인 합성

정규화 패스마다 `(출력 문자열, 그 패스 기준 SpanMap)` 을 내고, `SpanMap::compose` 로 합친다.
단조 테이블 두 개의 합성은 병합 한 번이라 O(n+m) 이다. 이렇게 하면 한글 수사 파서와 구분자 정규화를
독립적으로 테스트할 수 있고, 나중에 패스를 추가해도 매핑 코드가 바뀌지 않는다.

```rust
impl SpanMap {
    /// 변환 없는 항등 매핑
    pub fn identity(text: &str) -> Self;

    /// inner 를 먼저, outer 를 나중에 적용한 결과와 동등한 매핑을 만든다.
    /// 두 테이블 모두 단조이므로 단일 병합 순회로 끝난다.
    /// inner 의 출력 좌표계와 outer 의 입력 좌표계가 다르면 에러다.
    pub fn compose(inner: &SpanMap, outer: &SpanMap) -> Result<SpanMap>;

    /// 정규화문 구간을 원문 구간으로 되돌린다. 경계 스냅과 근거를 함께 낸다.
    pub fn to_source(&self, dst: &Span) -> SourceSpan;

    /// 아래 네 불변식 중 피복·연속·종류 정합성을 검사한다.
    pub fn validate(&self) -> Result<()>;
}

pub struct SourceSpan {
    /// 원문 기준 스팬
    pub span: Span,
    /// 세그먼트 경계 바깥으로 넓혀졌는지
    pub snapped: bool,
    /// 이 구간에 적용된 정규화 규칙 목록
    pub rules: Vec<RuleId>,
    /// 신뢰도 감점에 쓰이는 정규화 비용
    pub cost: NormalizationCost,
}

/// 이 스팬이 원문에서 얼마나 멀어졌는지의 정량 지표
pub struct NormalizationCost {
    /// 흡수한 공백 문자 수 (가장 위험하다)
    pub absorbed_whitespace: u16,
    /// 흡수한 구분자 수 (하이픈, 점, 괄호)
    pub absorbed_separators: u16,
    /// 숫자로 바뀐 한글 음절 수
    pub expanded_syllables: u16,
    /// 치환된 문자 수 (전각, 유사문자)
    pub replaced_chars: u16,
}
```

### 질의도 바이트와 문자를 함께 준다

`to_source` 는 정규화문 스팬을 `Range<u32>` 하나가 아니라 `Span`(바이트와 문자 둘 다)으로 받는다.
항등 구간 안에서 부분 매핑을 하려면 구간 시작으로부터의 **문자** 거리를 알아야 하는데,
바이트 오프셋만으로는 텍스트를 다시 훑지 않고서는 그것을 구할 수 없기 때문이다.
탐지 층 스캐너는 문자 단위로 순회하므로 두 좌표를 이미 들고 있다. 넘겨받으면 텍스트 재순회가 사라진다.

### 규칙 목록은 왜 정렬하는가

`rules` 는 적용 순서가 아니라 **이름 오름차순**으로 정규화된다. 구현 중 실측으로 드러난 문제 때문이다.
`compose(compose(a, b), c)` 와 `compose(a, compose(b, c))` 는 최종 스팬·종류·비용이 모두 같지만,
중간 단계에서 세그먼트가 묶이는 굵기가 달라 규칙이 수집되는 순서가 뒤집힌다. 순서를 그대로 두면
파이프라인을 어떻게 조립했느냐에 따라 출력이 달라져 결정성이 깨진다. 판정 근거로 필요한 것은
"어떤 규칙들이 관여했는가"라는 집합이지 순서가 아니므로, 정렬로 정규화해 결합법칙을 완전하게 만든다.

### 경계 스냅 규칙

탐지 스팬이 비항등 세그먼트를 가로지르는 경우가 있다. `일억` 이 `100000000` 으로 늘어난 뒤
그 안의 `100000` 만 매칭되는 상황이다. 이때 **세그먼트 경계 바깥으로 넓혀 원자성을 지키고,
넓어졌다는 사실을 `snapped: true` 로 판정 근거에 남긴다.**

매치를 폐기하는 방식이 더 안전하지만 재현율을 깎는다. 넓히는 쪽을 택하되, 넓어진 스팬은
검증 단계에서 다시 체크섬을 통과해야 하므로 잘못된 확장이 최종 결과로 나가지 않는다.

### 검증 하네스

네 개의 불변식을 속성 테스트(property test)로 강제한다. 완료 기준을 실제로 재는 장치다.

| 불변식 | 내용 |
| --- | --- |
| **피복** | 모든 정규화 오프셋이 정확히 하나의 세그먼트에 속한다. 세그먼트는 정렬되어 있고 빈틈과 겹침이 없다 |
| **왕복** | 임의의 탐지 스팬에 대해, 원문의 해당 구간을 다시 정규화한 결과가 정규화문의 해당 구간과 같다 (스냅 반영 후) |
| **무손실 마스킹** | 마스킹 결과에서 탐지 스팬 바깥의 바이트는 원문과 바이트 단위로 완전히 동일하다 |
| **합성 결합법칙** | `compose(compose(a, b), c)` 와 `compose(a, compose(b, c))` 의 결과가 같다 |

무손실 마스킹 불변식이 성립하면 "원문 복원 실패 0건"은 정의상 보장되고,
남는 위험은 스팬 경계 오류 하나로 좁혀진다. 그 경계 오류를 왕복 불변식이 잡는다.

## 7. 정규화 층 설계

패스는 순서대로 적용되고, 각 패스는 자기 SpanMap 을 낸다.

| 순서 | 패스 | 하는 일 | 세그먼트 종류 |
| --- | --- | --- | --- |
| 1 | `nfc` | 유니코드 정규화 형식 C 적용. 자모 분리형 한글을 음절로 합친다 | Replace |
| 2 | `fold` | 전각 숫자와 영문을 반각으로. 유사문자 교정 | Replace |
| 3 | `hangul` | 한글 수사를 숫자로 역변환 | Expand 또는 Replace |
| 4 | `separator` | 숫자 사이의 하이픈, 점, 공백, 괄호를 흡수 | Delete |

### 자모 분리형 한글을 왜 다루는가

macOS 계열에서 만들어진 텍스트와 일부 입력기 출력은 한글을 자모 분리형으로 담는다.
정규화 형식 C 를 첫 패스로 넣지 않으면 그런 입력에서 조용히 미탐이 난다. 순수 Rust 크레이트로
처리하므로 외부 함수 인터페이스 0 원칙에 위배되지 않는다.

### 구분자 흡수의 범위 제한

공백을 전역으로 지우면 `제품 1234 수량 5678` 이 `제품12345678` 이 되어 없던 숫자열이 생긴다.
그래서 **구분자 흡수는 숫자와 숫자 사이에서만** 일어난다. 그래도 위험은 남으므로,
흡수한 공백 개수를 `NormalizationCost.absorbed_whitespace` 에 기록해 신뢰도에서 차감한다.
하이픈 흡수는 위험이 훨씬 낮으므로 감점 계수가 다르다.

## 8. 한글 수사 역변환 설계

성숙한 기존 라이브러리가 없어 자체 구현 대상이다. 기존 한국어 수사 라이브러리는 대부분
숫자에서 한글로 가는 방향만 다룬다. 역방향이 필요하다.

### 두 가지 읽기 문법

한국어 수사 표기는 문법이 두 개이고, 이 둘을 구분하는 파서가 필요하다. 표 하나로 끝나지 않는 이유다.

| 문법 | 규칙 | 예시 |
| --- | --- | --- |
| **자릿수 읽기** | 음절 하나가 숫자 한 자리. 단위 음절이 없다 | `팔팔공일공일` → `880101`, `공일공` → `010` |
| **단위 읽기** | 십, 백, 천, 만, 억 단위를 계산한다 | `구십일` → `91`, `이천이십사` → `2024`, `천구백팔십팔` → `1988` |

판별 규칙은 단순하다. **런 안에 단위 음절(십, 백, 천, 만, 억)이 하나라도 있으면 단위 읽기,
없으면 자릿수 읽기.** 혼합 표기(`구십일년 삼월`)는 조사와 단위 명사(년, 월, 일)로 런을 끊은 뒤
각 런에 규칙을 적용한다.

### 자릿수 매핑

- 0: 공, 영, 빵
- 1: 일, 하나
- 2: 이, 둘
- 3: 삼, 셋
- 4: 사, 넷
- 5: 오, 다섯
- 6: 육, 륙, 여섯
- 7: 칠, 일곱
- 8: 팔, 여덟
- 9: 구, 아홉

### 오탐 억제

`사구`, `이사`, `구이` 처럼 일상어와 수사 음절이 겹치는 경우가 많다. 세 가지 게이트를 둔다.

- **최소 런 길이.** 기본 6음절 이상일 때만 자릿수 읽기를 적용한다. 설정 가능하다
- **숫자 문맥 인접.** 런 길이가 3-5음절이면 숫자 표지(`년`, `월`, `일`, `번`, `호`, 하이픈, 인접 숫자)가
  붙어 있을 때만 적용한다
- **후단 검증에 위임.** 위 두 게이트를 통과해도 최종 판정은 체크섬과 날짜 유효성이 한다.
  설계 원칙 "정규화는 관대하게, 검증은 엄격하게" 가 여기서 작동한다

## 9. 탐지 층 설계

### 스캔 방식

정규화 층이 이미 구분자를 흡수했으므로, 숫자 계열 엔티티 탐지는 **숫자 런 스캔 후 길이별 분류**로 환원된다.
정규 표현식보다 빠르고 결정적이며, 파국적 역추적 위험이 없다. 이메일처럼 구조가 복잡한 항목만
정규 표현식을 쓴다.

### 신뢰도 모델

이산 등급과 연속 점수를 함께 낸다. 컴플라이언스 용도라 "왜 이 등급인가"가 설명 가능해야 한다.

| 등급 | 조건 |
| --- | --- |
| `Certain` | 체크섬 통과. 예: 카드번호 Luhn 통과, 2020년 10월 이전 발급 주민등록번호 |
| `Probable` | 형식 일치 + 문맥 단서 충족. 체크섬이 없거나 적용 불가한 엔티티 |
| `Possible` | 형식만 일치. 문맥 단서 없음 |

연속 점수는 다음처럼 합산한다. 가중치는 설정 가능하다.

```text
score = 패턴 기본점
      + 체크섬 통과 가산점
      + 문맥 단서 가산점 (단서 종류와 거리에 따라)
      - 정규화 비용 감점 (흡수 공백 > 흡수 구분자 > 확장 음절 순으로 무겁게)
```

### 문맥 점수

계좌번호처럼 숫자열만으로는 판별 불가능한 엔티티에 필수다. 스팬 주변 설정 가능한 창 안에서
단서 단어를 찾아 가산한다. 은행명, `계좌`, `입금`, `이체`, `송금`, `예금주` 같은 단어다.
창 크기와 단어별 가중치는 설정으로 노출한다.

### 판정 근거

모든 Finding 은 근거를 동반한다. 이것이 컴플라이언스 도구로서의 최소 요건이다.

```rust
pub struct Evidence {
    /// 매칭된 패턴 규칙 이름
    pub rule: &'static str,
    /// 체크섬 결과. 적용 불가면 그 사유까지 담는다
    pub checksum: ChecksumResult,
    /// 잡힌 문맥 단서와 스팬으로부터의 거리
    pub context_hits: Vec<ContextHit>,
    /// 이 스팬에 적용된 정규화 규칙 목록
    pub normalizations: Vec<RuleId>,
    /// 정규화 비용 (신뢰도 감점 근거)
    pub cost: NormalizationCost,
    /// 세그먼트 경계로 확장됐는지
    pub snapped: bool,
}

pub enum ChecksumResult {
    Passed,
    Failed,
    /// 해당 엔티티에 검증식이 없거나 이 값에는 적용되지 않음
    NotApplicable(&'static str),
}
```

### 왜 안 걸렸는가도 설명한다

형식은 맞았는데 검증에서 떨어진 후보를 `Rejection` 으로 따로 낼 수 있다.
`검증되지 않은 개인정보가 지나갔다` 는 의심을 조사할 때 필요하다.

```rust
pub struct Rejection {
    pub entity: EntityKind,
    pub source: Span,
    pub reason: RejectReason,   // ChecksumFailed | InvalidDate | NoContext | BelowThreshold
}
```

## 10. 엔티티별 검증 수단

| 엔티티 | 검증 수단 | 도달 가능 최고 등급 | 비고 |
| --- | --- | --- | --- |
| 주민등록번호 | 앞 6자리 날짜 유효성 + 성별코드 범위 + 체크섬 | `Certain` 또는 `Probable` | **체크섬은 2020년 10월 이전 발급분에만 성립한다는 전제를 구현 전 검증해야 한다.** 이후 발급분은 뒷자리 임의화로 검증식이 없으므로 최고 등급이 `Probable` 로 내려간다 |
| 외국인등록번호 | 주민등록번호와 유사 구조, 성별코드 범위가 다름 | `Certain` 또는 `Probable` | 주민등록번호와 같은 전제 확인 필요 |
| 사업자등록번호 | 체크섬 | `Certain` | **가중치 방식이 알려져 있으나 구현 전 검증할 것** |
| 운전면허번호 | 형식 12자리 + 지역코드 | `Probable` | **검증 자릿수 알고리즘의 공개 정보가 불확실하다.** 확인되지 않으면 형식 검사만 하고 그 사실을 이 문서에 명시한다 |
| 여권번호 | 형식 | `Probable` | 구여권과 신여권 형식이 다르다 |
| 카드번호 | Luhn | `Certain` | **유일하게 확실한 표준 체크섬** |
| 계좌번호 | 은행 프리픽스 + 문맥 단서 | `Probable` | 은행별 7-14자리, 하이픈 위치가 제각각. **오탐 위험이 가장 크다.** 문맥 점수 없이는 `Possible` 이하 |
| 전화번호 | 형식 | `Probable` | 휴대폰, 유선, 대표번호를 구분한다 |
| 이메일 | 형식 | `Probable` | |
| 생년월일 | 날짜 유효성 + 문맥 | `Probable` | 변형 표기가 가장 다양하다. 문맥 없이는 일반 날짜와 구분되지 않는다 |

**"도달 가능 최고 등급" 열이 이 표의 핵심이다.** `Certain` 에 도달할 수 없는 엔티티는
구조적으로 오탐을 완전히 없앨 수 없다. 그 사실을 감추지 않는다.

## 11. 마스킹 층 설계

### 정책 4종

| 정책 | 동작 | 가역성 |
| --- | --- | --- |
| `Redact` | 전체를 고정 문자열로 치환 (`[주민등록번호]` 또는 `*` 반복) | 불가역 |
| `Partial` | 일부만 노출 (`880101-1******`) | 불가역 |
| `Hash` | 솔트를 넣은 해시 기반 메시지 인증 코드(HMAC)로 가명화. 같은 값은 항상 같은 토큰이 되므로 통계 분석이 가능하다 | 불가역, 연결성 유지 |
| `Tokenize` | 치환하고 복원 맵을 함께 낸다 | **완전 가역** |

정책은 엔티티별로 다르게 줄 수 있다. 주민등록번호는 전체 치환, 전화번호는 부분 노출 같은 조합이 가능하다.

### 복원 보장

- `Tokenize` 정책: `unmask(mask(text).text, restore_map)` 이 원문과 **바이트 단위로 완전히 같다**
- 모든 정책 공통: 마스킹 결과에서 탐지 스팬 바깥의 바이트는 원문과 **바이트 단위로 완전히 같다**

두 번째 보장이 더 근본적이다. 이것이 성립하면 마스킹이 문서를 조용히 훼손하는 일이 원천적으로 없다.
Presidio 의 복원 실패 36퍼센트가 정확히 이 보장의 부재에서 온다.

## 12. 합성 검증 코퍼스

실제 주민등록번호를 테스트에 넣을 수 없다. 그래서 **체크섬이 유효한 합성 데이터 생성기를 함께 만든다.**
이것은 부산물이 아니라 독립적 가치가 있는 모듈이고, 변형 표기 회귀 테스트셋의 기반이다.

생성기가 내는 것

- 체크섬이 유효한 각 엔티티 샘플 (주민등록번호, 사업자등록번호, 카드번호)
- 같은 값의 변형 표기 파생물: 순수 숫자열, 하이픈 표기, 공백 표기, 한글 자릿수 읽기, 한글 단위 읽기, 혼합 표기, 전각 표기
- 문맥이 있는 문장과 없는 문장 쌍
- 오탐 유도 음성 샘플: 체크섬이 틀린 유사 숫자열, 수사 음절로 이루어진 일상어, 주문번호와 제품번호

**회귀 테스트는 이 코퍼스에서 재현율과 정밀도를 숫자로 낸다.** "잘 된다"는 완료가 아니다.

## 13. 공개 API 초안

```rust
use rust_pii_transformer::{Config, PolicySet, detect, mask, unmask};

// 탐지만
let findings = detect(text, &Config::default());

// 마스킹
let out = mask(text, &Config::default(), &PolicySet::default());
println!("{}", out.text);

// 토큰화 정책이면 완전 복원
if let Some(restore) = &out.restore {
    let recovered = unmask(&out.text, restore)?;
    assert_eq!(recovered, text);
}
```

핵심 타입

```rust
pub struct Finding {
    pub entity: EntityKind,
    /// 원문 기준 스팬
    pub source: Span,
    /// 정규화문 기준 스팬
    pub normalized: Span,
    pub certainty: Certainty,
    pub score: f32,
    pub evidence: Evidence,
}

pub struct Span {
    pub byte: Range<u32>,
    pub char: Range<u32>,
}

pub struct MaskOutput {
    pub text: String,
    pub findings: Vec<Finding>,
    /// Tokenize 정책일 때만 존재
    pub restore: Option<RestoreMap>,
}
```

오프셋을 `u32` 로 둔 이유는 둘이다. 4기가바이트를 넘는 단일 텍스트는 이 라이브러리의 용도가 아니고,
세그먼트 하나가 오프셋을 8개 들고 다니므로 절반 크기가 그대로 메모리 절감이 된다.

`Finding` 은 `serde` 직렬화를 지원하므로 그대로 JSON 으로 낼 수 있다. 단 **역직렬화는 지원하지 않는다.**
규칙 식별자를 `&'static str` 로 두어 힙 할당을 없앴는데, 그것을 역직렬화하려면 입력 수명이 `'static`
이어야 하고 그것을 만족시킬 방법이 없기 때문이다. 이 라이브러리의 용도는 판정 결과를 내보내는 것이지
되읽는 것이 아니므로 이 교환을 택했다.

## 14. 명령줄 도구 rpit

바이너리 이름은 `rpit` 이다. 이 패밀리의 명명 규칙(`r` + 도메인 축약 + `t`)을 따르되,
3글자 약어는 앞 2글자를 남기는 선례에 맞춰 `pii` 에서 `pi` 를 남겼다.

```bash
# 탐지 결과를 JSON 으로
rpit detect --input sample.txt --format json

# 마스킹
rpit mask --input sample.txt --policy redact --output masked.txt

# 토큰화 마스킹과 복원 맵 저장
rpit mask --input sample.txt --policy tokenize --restore-map map.json

# 복원
rpit unmask --input masked.txt --restore-map map.json

# 왜 안 걸렸는지 조사 (형식은 맞았으나 검증에서 떨어진 후보 표시)
rpit explain --input sample.txt

# 합성 검증 데이터 생성
rpit synth --entity rrn --variants all --count 100
```

명령줄 도구는 `cli` 기능 플래그를 켰을 때만 빌드된다. 라이브러리 소비자에게 `clap` 의존성이 새지 않도록
옵트인으로 둔다.

## 15. Python 바인딩

PyO3 로 abi3(파이썬 안정 이진 인터페이스) 휠을 만들어 Python 3.9 이상 전 플랫폼에서
Rust 툴체인 없이 설치되게 한다. **구현돼 있고 동작한다.** 단 노출 범위는 지금 실제로 도는
`span` 층까지다. `detect` 와 `mask` 는 **함수 자체를 만들지 않았다** — 던지기만 하는 껍데기를
미리 노출하면 소비자가 그것을 있는 기능으로 오해하기 때문이다. 현재 범위는 런타임에서
`rust_pii_transformer.__status__` 로 확인할 수 있다.

### 지금 쓸 수 있는 것

```python
import rust_pii_transformer as rpit

rpit.__status__          # 'span layer only — normalize, detect, and mask are not implemented yet'

# 정규화 패스 하나를 흉내 낸다. "880101-1234567" 에서 하이픈을 흡수한다.
b = rpit.SpanMapBuilder()
b.keep("880101")
b.absorb("-", "separator.hyphen", "separator")
b.keep("1234567")
normalized, smap = b.finish()          # '8801011234567'
smap.validate()                        # 불변식이 깨졌으면 SpanMapError

# 정규화문에서 찾은 스팬을 원문 좌표로 되돌린다.
src = smap.to_source(rpit.Span(0, 13, 0, 13))
src.byte_start, src.byte_end           # (0, 14) — 원문에서는 하이픈까지 14바이트
src.snapped                            # False
src.rules                              # ['separator.hyphen'] — 판정 근거
src.cost.absorbed_separators           # 1
```

### 문자 좌표가 1급 시민이다

Python 문자열은 문자 인덱스 기반이라 바이트 오프셋만 주면 소비자 쪽에서 다시 변환해야 하고,
그 변환이 새로운 오프셋 버그의 출처가 된다. 그래서 모든 스팬이 두 좌표를 함께 내고,
문자 좌표만 아는 흔한 상황을 위한 진입점을 따로 둔다.

```python
start = normalized.index("880101")     # Python 의 index 는 문자 기준이다
src = smap.to_source_from_chars(normalized, start, start + 6)
src.span.slice(source_text)            # 원문 조각을 그대로 잘라 낸다
```

### 공개 표면

| 이름 | 내용 |
| --- | --- |
| `Span(byte_start, byte_end, char_start, char_end)` | 구간. `Span.from_char_range(text, s, e)` 로 문자 좌표만으로도 만든다. `slice(text)` 로 조각을 낸다 |
| `SpanMapBuilder(text=None)` | `keep` · `replace` · `numeral` · `absorb` 로 조각을 넘기고 `finish()` 가 `(정규화문, SpanMap)` 을 낸다 |
| `SpanMap` | `identity(text)` · `compose(inner, outer)` · `to_source(span)` · `to_source_from_chars(...)` · `validate()` · `segments` · `to_json()` |
| `SourceSpan` | `span` · `byte_start` · `char_start` · `snapped` · `rules` · `cost` · `to_json()` |
| `Segment` · `NormalizationCost` | 세그먼트 내성과 정규화 비용 |
| `SpanMapError` | 불변식 위반과 좌표계 불일치 |

`absorb` 의 세 번째 인자는 `"whitespace"` · `"separator"` · `"other"` 중 하나다. 종류마다 신뢰도
감점 계수가 다르므로 정확히 골라야 하고, 다른 값을 주면 `ValueError` 가 난다.

### 경계에서 지키는 두 가지

- **패닉을 Python 으로 넘기지 않는다.** 코어의 `Span::slice` 는 범위 밖에서 패닉하고, `finish` 는
  빌더를 소비한다. 바인딩은 그 앞에서 검사해 `ValueError` 와 `RuntimeError` 로 바꾼다.
  인터프리터를 죽이는 대신 잡을 수 있는 예외를 낸다.
- **코어를 오염시키지 않는다.** `span` 의 타입에 `#[pyclass]` 를 직접 달지 않고 `src/python.rs`
  안의 래퍼에만 붙인다. 그래서 기본 빌드에는 PyO3 가 전혀 들어오지 않는다(16절 독립성 원칙).

### 알려진 대가: 규칙 이름 인터닝

코어는 규칙 이름을 `&'static str` 로 들고 다녀 힙 할당을 0 으로 만든다(6절). 그 선택이 Python
경계에서 대가를 만든다. 런타임에 들어온 문자열에는 `'static` 수명이 없으므로 누출로 승격시켜야
한다. 같은 이름은 한 번만 누출되도록 풀에 담으므로, 규칙 이름이 설계대로 고정된 소수 집합이면
풀 크기는 상수에 수렴한다.

**호출자가 매번 새 규칙 이름을 만들어 넣으면**(예: 반복문에서 `f"rule.{i}"`) **그만큼 메모리가
누적되고 회수되지 않는다.** 규칙 이름은 상수로 두고 가변값은 다른 인자로 넘기는 것이 올바른
사용법이다.

### 노출하지 않은 것

`SpanMapBuilder.insert` 는 코어에 있지만 Python 으로 내지 않았다. 현재 정규화 파이프라인이 쓰지
않는 경로이고, 합성 시 불변식과 결합법칙이 깨지는 것이 실측으로 확인됐기 때문이다
([18. 알려진 한계](#18-알려진-한계)). 그 경로가 정리되면 함께 추가한다.

## 16. 빌드와 Cargo Feature

```toml
[lib]
crate-type = ["rlib", "cdylib"]

[features]
# 코어(오프셋 매핑, 정규화, 탐지, 전체치환·부분노출·토큰화 마스킹)는 항상 빌드된다.
default = []
# Python 바인딩(PyO3 cdylib). abi3 휠.
python  = ["dep:pyo3", "dep:serde_json"]

[dependencies]
thiserror  = "2"
serde      = { version = "1", features = ["derive"] }
pyo3       = { version = "0.29", optional = true, features = ["extension-module", "abi3-py39"] }
serde_json = { version = "1", optional = true }
```

**아래 feature 는 아직 선언돼 있지 않다.** 해당 코드가 실제로 들어오는 단계에서 함께 추가한다.
켤 수 없는 feature 를 미리 선언하면 그것을 켜 본 사람이 빌드 실패를 만나기 때문이다.

| feature | 끌어오는 의존성 | 들어오는 단계 |
| --- | --- | --- |
| `hash` | `sha2`, `hmac` | 마스킹 층 |
| `synth` | `rand` | 합성 검증 코퍼스 |
| `cli` | `clap` | 명령줄 도구 |

같은 이유로 `[[bin]]` 항목은 명령줄 도구 단계에서 만든다. `pyproject.toml` 은 Python 바인딩이
실제로 들어왔으므로 이미 있다.

### 최소 Rust 버전

기본 빌드는 **1.71** 이면 된다(`thiserror` 2 가 상한). `--features python` 은 PyO3 0.29 때문에
**1.83** 이 필요하다. 옵트인 경로 하나 때문에 코어 소비자 전체를 1.83 으로 올리지 않으려고
`package.rust-version` 은 1.71 로 두고 차이를 여기에 적는다.

**독립성 원칙: 기본 빌드는 순수 Rust, 외부 함수 인터페이스 0, 하위 프로세스 호출 0.**
모든 의존 크레이트가 순수 Rust 이므로 정적 빌드가 가능하고, 폐쇄망에서 그대로 돈다.

```bash
# 라이브러리
cargo build

# 테스트
cargo test
cargo clippy --all-targets -- -D warnings

# Python 확장 (개발 설치) — pyproject.toml 이 features = ["python"] 을 이미 지정한다
pip install maturin
maturin develop
pytest tests/test_python_binding.py

# Python 바인딩까지 포함한 검사
cargo clippy --features python --all-targets -- -D warnings
```

maturin 없이 확장 모듈을 확인하려면 cargo 로 cdylib 를 만든 뒤 확장자만 바꿔 경로에 두면 된다.
플랫폼별 산출물 이름이 다르다.

```bash
cargo build --features python --release
# Windows:  target/release/rust_pii_transformer.dll     -> rust_pii_transformer.pyd
# Linux:    target/release/librust_pii_transformer.so   -> rust_pii_transformer.so
# macOS:    target/release/librust_pii_transformer.dylib -> rust_pii_transformer.so
```

## 17. 개발 로드맵과 현재 상태

상태는 세 가지로만 표기한다. **동작 확인**은 실제로 실행해 결과를 본 것이고,
**코드만 존재**는 작성됐으나 검증되지 않은 것이며, **미구현**은 아직 없는 것이다.

| 단계 | 산출물 | 검증 수단 | 상태 |
| --- | --- | --- | --- |
| 0 | 레포 골격 (`Cargo.toml`, `LICENSE`, `.gitignore`, `src/lib.rs`, `src/error.rs`) | `cargo build` 통과 | **동작 확인** |
| 1 | 오프셋 매핑 설계 확정 | 이 문서 6절 | **완료** |
| 2 | `span` 모듈 (`SpanMap`, `Segment`, `compose`, `to_source`, `validate`) | 단위 테스트 18건 + 무작위 불변식 400회 통과 | **동작 확인** |
| 3 | `normalize` 모듈 (4개 패스) | 왕복 불변식 테스트 | 미구현 |
| 4 | `synth` 합성 데이터 생성기 | 생성물이 자기 검증기를 통과 | 미구현 |
| 5 | `detect` 모듈 (엔티티별 인식기, 체크섬, 문맥 점수) | 합성 코퍼스 기준 재현율·정밀도 수치 | 미구현 |
| 6 | `mask` 모듈 (정책 4종, 복원) | 왕복 복원 실패 0건 | 미구현 |
| 7a | Python 바인딩 (`src/python.rs`, `pyproject.toml`) | Python 테스트 24건 통과, `cargo clippy --features python` 경고 0 | **동작 확인** |
| 7b | 명령줄 도구 `rpit` | `cargo test`, `cargo clippy` | 미구현 |

단계 7a 를 5·6 보다 먼저 한 것은 순서를 앞당긴 것이 아니라 **노출 범위를 그 시점의 구현으로
제한했기** 때문이다. 바인딩은 지금 실제로 도는 `span` 층만 낸다. 탐지·마스킹 층이 들어오면
그때 같은 파일에 함수를 추가한다. 바인딩 검증은 확장 모듈을 실제로 적재해 Python 에서 주행하는
방식으로 했고(Windows·CPython 3.12·abi3-py39 휠), 원문 좌표 복원·경계 스냅·한글 바이트와 문자
좌표 분리·합성·JSON 내보내기·예외 변환을 모두 확인했다.

단계 2까지의 검증 상태를 구체적으로 적으면 이렇다. 네 불변식 중 **피복·합성 결합법칙**은 구현되어
테스트로 강제되고 있고, **왕복**과 **무손실 마스킹**은 각각 정규화 층과 마스킹 층이 있어야 검증 가능하므로
아직 미검증이다. 무작위 테스트는 고정 시드 선형 합동 생성기로 400라운드를 돌려 피복·좌표계 보존·
결합법칙·스팬 경계를 확인한다. 외부 속성 테스트 크레이트를 쓰지 않은 것은 기본 빌드의 의존성 0 원칙을
개발 의존성에도 그대로 적용했기 때문이다.

단계 순서에는 이유가 있다. **가장 싸게 확신을 얻는 순서**다. 오프셋 매핑이 안 되면 나머지가 전부
의미가 없으므로 그것부터 확정했고, 정규화 층이 되면 남은 것은 정규식과 체크섬이라 진행이 빠르다.

### 완료 기준

- 변형 표기 회귀 테스트셋에서 재현율과 정밀도를 **숫자로** 제시한다
- 마스킹 왕복 테스트에서 **원문 복원 실패 0건**
- `cargo test` 전체 통과, `cargo clippy` 경고 정리
- 기본 기능만으로 외부 동적 라이브러리 의존이 0
- 미구현과 미검증 범위를 이 문서에 정직하게 명시

### 17.1 배포 전 관문

**아직 crates.io 와 PyPI 어느 쪽에도 게시하지 않았다.** 기술적으로는 지금도 게시할 수 있지만
하지 않는 이유가 있다. 패키지 이름과 설명이 약속하는 것은 한국어 개인정보 탐지·마스킹인데
현재 제공하는 것은 오프셋 매핑 자료구조 하나다. 검색으로 유입된 사람이 탐지를 기대하고 설치했다가
아무것도 못 잡는 상황을 만들지 않는다. 게시는 되돌릴 수 없다 — crates.io 는 삭제가 아니라
yank 만 되고, PyPI 도 같은 버전 번호를 다시 쓸 수 없다.

게시 전에 통과해야 할 것.

| 관문 | 내용 | 상태 |
| --- | --- | --- |
| `insert` 경로 정리 | 합성 시 불변식·결합법칙이 깨지는 것이 실측됨. 제거하거나 고친다 | 미해결 |
| 탐지·마스킹 동작 | 단계 5·6 완료. 이름이 약속하는 기능이 실제로 있어야 한다 | 미해결 |
| 재현율·정밀도 수치 | 합성 코퍼스 기준 숫자 제시 | 미해결 |
| 지속적 통합 | 다중 플랫폼 `cargo test` · `clippy` · 휠 빌드 자동화 | 미해결 |
| 다중 플랫폼 휠 | 현재 Windows CPython 3.12 에서만 실측. Linux · macOS 미검증 | 미해결 |

이름 선점이 급하면 `0.0.x` 로 범위를 설명에 명시해 올리는 선택지가 있으나, 그것도 위 `insert`
관문은 먼저 통과해야 한다.

## 18. 알려진 한계

숨기지 않는 것이 이 절의 목적이다.

### 구조적 한계 (규칙 기반이 원리적으로 못 하는 것)

- **문맥 없는 숫자열은 판별 불가능하다.** `1234567890` 이 계좌번호인지 주문번호인지, 규칙만으로는 알 수 없다.
  문맥 단서가 없으면 `Possible` 등급 이상으로 올리지 않는다
- **이름과 주소는 탐지하지 않는다.** 규칙이 없다. 개체명 인식 백엔드를 옵트인으로 붙일 인터페이스만 열어 둔다
- **고민감도 항목의 재현율은 낮다.** 다국어 벤치마크에서 규칙 기반 탐지기가 이 영역에서 무너지는 것이
  이미 관측돼 있다. 이 라이브러리도 예외가 아니다
- **생년월일은 일반 날짜와 구분되지 않는다.** 문맥 단서에 전적으로 의존한다

### 확인된 결함: `insert` 세그먼트 경로

`SpanMapBuilder::insert` 와 `SegmentKind::Insert` 는 "확장 대비"로 두었으나 **실측으로 두 가지
결함이 확인됐다.** 현재 정규화 파이프라인(7절의 4개 패스)이 이 경로를 쓰지 않아 실사용 피해는
없지만, `insert` 는 공개 API 라 외부 소비자가 지금 호출할 수 있다.

- **합성 결과가 불변식 검사를 통과하지 못한다.** 앞 패스가 삽입한 문자를 뒤 패스가 흡수하면
  양쪽이 모두 빈 퇴화 세그먼트가 남고, 그것이 `Insert` 로 분류되어 `validate` 가 거부한다
- **합성 결합법칙이 깨진다.** `compose(compose(a, b), c)` 와 `compose(a, compose(b, c))` 가
  둘 다 검사를 통과하면서도 세그먼트가 묶이는 굵기가 달라진다. 규칙 목록 정렬로 해결했던
  것과 같은 종류의 순서 의존이 세그먼트 단위에 남아 있다

레포 자체 테스트가 이것을 놓친 이유는 무작위 불변식 테스트의 연산 목록에 `insert` 가 없어
해당 분기가 한 번도 실행되지 않았기 때문이다. **Python 바인딩은 이 경로를 노출하지 않는다.**
정리 방향(제거 또는 수정)이 정해지면 무작위 테스트에 `insert` 를 넣어 함께 강제한다.

### 구현 전 검증이 필요한 사항

아래 세 항목은 **공개 정보의 신뢰도가 확인되지 않았다.** 구현 착수 전에 근거를 확인하고,
확인되지 않으면 형식 검사만 수행한 뒤 그 사실을 이 절에 남긴다.

- 주민등록번호 체크섬이 2020년 10월 이후 발급분에서 성립하지 않는다는 전제
- 사업자등록번호 체크섬 가중치 방식
- 운전면허번호 검증 자릿수 알고리즘의 존재 여부와 공개 여부

### 정규화의 대가

"정규화는 관대하게" 원칙은 검증 수단이 강한 엔티티에서만 안전하다. 계좌번호와 생년월일처럼
체크섬이 없는 엔티티는 관대한 정규화가 그대로 오탐률 상승으로 이어진다.
정규화 비용 감점으로 완화하지만 제거하지는 못한다. 해당 엔티티의 임계값을 보수적으로 두는 것이
운영상 권장 사항이다.

## 19. 디렉토리 구조

현재 존재하는 것은 굵게 표시했다. 나머지는 계획이다.

- **`Cargo.toml`** 패키지, 기능 플래그, 의존성
- **`LICENSE`** Apache-2.0
- **`README.md`** 이 문서
- **`.gitignore`**
- **`pyproject.toml`** maturin 빌드 설정
- **`src/`**
  - **`lib.rs`** 공개 API 진입점
  - **`error.rs`** `thiserror` 기반 단일 에러 열거형
  - **`python.rs`** PyO3 바인딩 (`--features python`)
  - **`span.rs`** `SpanMap`, `Segment`, `Span`, `SpanMapBuilder`, `compose`, `to_source`, `validate`
  - `normalize/`
    - `mod.rs` 파이프라인 조립
    - `nfc.rs` 유니코드 정규화 형식 C
    - `fold.rs` 전각과 유사문자 폴딩
    - `hangul.rs` 한글 수사 역변환 (자릿수 읽기, 단위 읽기)
    - `separator.rs` 구분자 흡수
  - `detect/`
    - `mod.rs` 탐지 오케스트레이션과 신뢰도 산정
    - `scanner.rs` 숫자 런 스캐너
    - `context.rs` 문맥 단서 사전과 점수
    - `bank.rs` 은행 프리픽스 테이블
    - `entity/` 엔티티별 인식기와 체크섬
  - `mask/`
    - `mod.rs` 정책 적용
    - `policy.rs` 정책 4종
    - `restore.rs` 복원 맵
  - `synth/` 합성 검증 데이터 생성기
  - `bin/`
    - `rpit.rs` 명령줄 도구
- **`tests/`**
  - **`test_python_binding.py`** PyO3 바인딩 회귀 테스트 (pytest)
  - 통합 테스트와 속성 테스트는 각 층이 들어올 때 함께 추가
- `examples/` 사용 예제
